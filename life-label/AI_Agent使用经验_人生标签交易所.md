
# AI Agent 开发实践复盘：《人生标签交易所：试用期》

用 AI Agent（Claude）独立完成了一个单文件 Canvas 网页游戏的从设定到实现。全程约 27 小时（2026-06-15 11:22 起草世界观，到 06-16 14:51 完成 game.html），之后又用一次独立实验验证了架构可扩展性。以下是复盘出的方法论和踩坑记录。

## 项目概况

- **交付物**：`game.html`，单文件，2105 行，纯 Canvas 2D 渲染，无框架。
- **支撑材料**：`docs/` 下 8 份规格文档（世界观、UI、视觉风格、技术规格、数据 schema 等），`data/` 下 7 个 JSON 内容文件（案件、班次、标签、流向、结局、吉祥物文案）。
- **时间线**：先写世界观和游戏方案 → 半天内产出 UI/视觉/技术/数据规格 → 再产出结局设计和基础内容数据 → 最后一天生成案件库、班次数据并完成 `game.html` 实现。文档始终先于代码。

## 一、值得复用的方法

**先写规格文档，代码后动手。** 项目根目录的 `CLAUDE.md` 明确要求"开始任何任务前必须阅读"五份规格文档，且这些文档在 `game.html` 动笔前就已完整存在。好处是每次会话、每个子任务都有唯一可信来源，Agent 不会凭感觉发挥，也不会前后矛盾。

**把"不可协商"的约束写死在 CLAUDE.md 里，而不是靠自然语言叮嘱。** 例如：只能用 Canvas 2D、HTML 里只允许一个 `<canvas>` 标签、背景色和纸张色给出精确色值、禁止 `localStorage`/`alert`/`confirm`、核心交互必须是拖拽而非表单。这类"物理限制"比"请尽量……"式的指导更管用——它直接堵死了 Agent 引入 React、用 DOM 做 UI、用 localStorage 存档这些"更省事但违反约定"的路径，不给它留选择空间。

**内容和代码彻底分离。** 所有案件、班次、标签、流向文本都放在 `data/*.json`，运行时 `fetch` 加载；CLAUDE.md 直接写明"不得硬编码任何游戏内容"。好处有两个：一是内容生成可以完全交给其他 Agent 并行处理而不碰引擎代码；二是有一份四万字的 `DATA_SCHEMA.md` 独立定义校验规则，内容对不对可以脱离代码走查来判断。

**批量、机械化的内容生产，显式委派给另一个 Agent 实例，而不是在当前对话里连续跑几十条。** 项目里有一份临时笔记，记录了用户真实地这样做过一次：不让当前 Agent 直接生成剩余 20-30 个案件、7 个班次数据并合并 JSON，而是要求"编写清楚的指示，让另一个 AI Agent 完成任务，给我可直接复制的 prompt 文本，还有需要附上的文件清单"。这个模式的好处是：批量生成不占用主对话的上下文，子任务可以并行跑，产出也更容易用 `DATA_SCHEMA.md` 独立校验和验收。同一份笔记里用户还顺手指出了"tag 和 flow 的数量太少了"——说明这类可复用内容库的量级最好在定 schema 阶段就设最低数量目标，不要等实现完了才靠感觉去补。

**重构前先写"行为基线"文档，再动手拆分代码。** 项目后续在一个独立的 git worktree 里做过一次架构重构实验：把单文件 `game.html` 拆成 `data → core → presentation/input → app` 的分层结构。开工前先产出了 `REFACTOR_BASELINE.md`——逐行通读原 2105 行 `game.html`，记录的是"现状"而不是"应然"，并明确写着"重构任何一步后，行为都必须与本文件一致；如需偏离，必须显式说明"。这避免了重构类任务最常见的失败模式：一边重写一边悄悄改变行为，出了问题分不清是重构引入的 bug 还是本来的设计。

**用 git worktree 隔离高不确定性的实验，不动主线。** 上面这次重构没有在主目录进行，而是在独立 worktree 里完成，配上 Vite + TypeScript + Vitest（54 个用例覆盖案件操作、回单押金、结局、状态机、倾向系统等核心规则）。主目录的 `game.html` 和 `CLAUDE.md` 的"单文件"约束全程没被碰过——这个重构实验哪怕最后被放弃，也不影响试用期版本这条主线交付物。通用经验是：想探索"这个原型能不能长成正式工程"这类高不确定性问题时，用 worktree/分支隔离着做，别在满足当前约束的主分支上直接动刀。

**把规则层设计成不依赖渲染，测试可以脱离 UI 独立跑。** 那次重构的架构文档把 core 层设计成不依赖 Canvas/DOM/window，可以在 Node 环境下用 Vitest 单独跑，据文档说明是专门为将来可能移植到 Unity C# 做准备。54 个测试用例全部针对纯规则逻辑，不依赖界面，比截图回归更快更稳，也更适合 Agent 自己验收自己的改动。

## 二、踩过的坑

**修订规格文档时留下了未清理的旧版本。** `docs/` 目录下同时存在 `ENDING_DESIGN.md`（旧版，18:51 写成）和 `ENDINGS_DESIGN.md`（新版，21:43 写成，内容明显是前者的修订版）。两份文件都不在 CLAUDE.md 列出的"必读规格"清单里，等于是脱离了强制阅读机制的孤儿文档。风险在于：下次任务如果误读了旧版本，会拿到过时甚至互相矛盾的设计。教训是修订规格文档时应同步删除旧文件，或者明确标注废弃、不要让新旧版本并存。

**重构分支的规格文档与主线出现了分叉。** worktree 里的 `TECH_SPEC.md`（37584 字节）和 `DATA_SCHEMA.md`（36801 字节）与主目录同名文件（分别 38716、39766 字节）内容不同，说明重构过程中同步更新了规格文档，但没有合并回主线。如果之后决定把重构成果合并回主分支，需要专门做一次文档对齐，否则"任务开始前必须读"的规格文档会出现两个不一致的版本，Agent 读到哪份取决于它在哪个目录工作，容易出错。

## 三、可以直接抄的模板

1. 项目根放一份 `CLAUDE.md`：列出必读规格文档清单、渲染方式等"物理约束"、明确禁止项。
2. 内容数据一律放独立 JSON，代码只读不写死。
3. 大批量、结构化的内容生成任务，写清楚 prompt + 文件清单，委派给独立的 Agent 会话去跑。
4. 想验证"能不能重构/换架构"这类高风险问题，开 git worktree 单独做，写一份行为基线文档再动手，写完测试再收尾。
5. 定期检查规格文档目录有没有孤儿文件、多分支之间有没有内容分叉。
